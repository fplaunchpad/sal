No vacuous desired-answer premise or dropped uniqueness premise was found in these endpoints. The carrier result is intentionally valid for arbitrary queries, including constant queries; this is why it cannot itself establish editing correctness. `issuance.CanIssue := True` is a total carrier policy, not a claim that arbitrary payloads satisfy honest core allocation, origin completeness, successful preparation, or interval ownership. The exact representation theorem can hold even for conflicting facts that a future document renderer must reject or exclude by protocol invariants.

The executable and Lean carrier are separate artifacts. The executable retains full transaction payloads for collision checking, reference comparison and client reissuance, while the Lean fact state contains no transaction archive. The executable maintains sorted child indexes and maps with collision checks; the Lean state is a finset that can retain distinct conflicting rows/cuts/creates. Its physical function converts rows to a list and recomputes sorted traversal, rather than verifying the JavaScript child indexes. The typed block keys carry issued IDs, but rendering the initial creation's order also needs the canonical bootstrap identity/provenance. These are compatible design choices under honest protocol assumptions, but no executable-to-Lean simulation or extraction theorem is established here.

Remaining end-to-end obligations are material: define a structural document query over create links, origin rows and cut ownership; prove uniqueness/completeness and START/marker interval ownership from honest issuance; prove displayed create-origin traversal and block texts equal existing transaction-set reconstruction; derive the row bridge's successful replay/uniqueness premises from the existing protocol; connect structural updates and actual receipt/merge executions to that representation; then reuse the independent sequential history bridge on a common RA witness. Physical row correspondence alone does not prove split routing, final interval ownership, display order, local edit effects, or document RA correctness. No proof-work reduction, archive-free executable memory result, or production Notion correspondence follows from these modules.

## History transport and local issuance audit

Independently checked the updated `NotionCoreStructuralHistory.lean` with `lake env lean`; its five printed endpoints report only standard axioms. `versions_witness` reuses the literal reference `witness` list, event enumeration and independent `NotionCoreMRDT.spec`. It changes neither payload labels nor admitted output. The target required-order relation is empty because structural updates commute, just as the reference carrier updates do; visibility is copied exactly by `mapConfig`. Registered source archives are recovered only as proof witnesses from `mapVer_some_iff`, not reconstructed in the target state. `honest_version_agreement` derives registered-state correspondence and causal closure from actual reference `Protocol.Reach`, injective sessions and its existing certificate. Its sole new semantic premise is the explicitly named `ClosedQueryAgreement`. `protocol_execution_of_closed` derives the head agreement needed by operational transport. No second desired-output or stored-state-equality premise is hidden in these endpoints. Until the concrete renderer discharges that contract, these are conditional transport results.

The scope of local clients is narrower. Mapped raw operations are sufficient to establish that transactions actually issued by the existing honest reference factory/client trace execute on the structural carrier with the same witness and, after renderer discharge, the same answers. They do not establish that a structural client can prepare a new positional create/insert/delete/split request using only structural local state. Existing `CanIssue.Prepared` reconstructs the reference document and calls its positional `prepareRequest`; the benchmark similarly generates requests through the pinned `Replica` and times only receipt/merge/query. Equal visible block texts do not by themselves supply insertion origin selection, inherited zero-gap routing, per-instance deletion targets or atomic split payload preparation.

There is also a precise allocation-information gap. A pure erase contributes target facts but does not retain its own transaction ID/reservation. For a seed `ab`, erasing its first atom at source counter 3 or at counter 9 produces the same structural facts; the reference ordinary guard's next-counter freshness differs. The reference protocol permits source-counter gaps, so equality of semantic facts cannot in general recover that exact allocator guard. This allocation obstruction is now separately mechanized in `NotionCoreStructuralIssuanceBoundary`: `low_reachable` and `high_reachable` are actual honest `MachineNetwork.Reach` traces for the same positional erase request, with an explicit six-tick gap in the latter. `fact_clock_control` proves identical document facts and different clocks, `next_counter_control` pins counters 4 versus 10 and rejects counter 4 in the high allocator, and `next_counter_not_from_facts` refutes every fact-only recovery function on all honest reachable network states. I independently checked this module with Lean; its printed endpoints use standard axioms only. This is an allocation-information boundary, not a deletion bug, and is a source-network result rather than a separately constructed Sal protocol trace. An independent allocator clock/watermark carried as client metadata can address this loss, but it requires a stated update/receipt invariant. The executable currently retains the full archive and delegates allocation/preparation to the reference client.

Preserving the original honest client protocol is sufficient for the mapped core result requested here; direct structural preparation is a deferred optimization, rather than permission to enlarge issuance. A further claim that clients prepare locally from the fact state would need direct positional preparation and an allocation/receipt metadata invariant, then a refinement theorem showing its emitted payload is admitted by the original honest guard (or an equivalent guard proved in both directions). This audit does not propose replacing the existing protocol with `CanIssue := True` or enlarging its request bounds.
